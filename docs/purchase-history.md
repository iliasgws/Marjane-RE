## Navigation

`CustomerAccount` → “Historique de mes achats” → `MyPurchases`.
The screen has two top tabs: **En ligne** (`MyPurchasesOnlineScreen`) and
**En magasin** (`MyPurchasesStoreScreen`). See lines 1437706–1437720 and
1454715–1454855. Receipt details use `PurchaseDetails`; online orders have
separate order-detail and delivery-tracking routes.

Balance/Carnet history is a different feature. Earlier notes conflated wallet
balance history with Carnet/Wafasalaf operations; do not treat them as the same API.

## In-store receipts: request flow

The configured API base in native `BuildConfig.java` is
`https://api-ayaline.marjane.ma`.

The list saga reads `auth.profile.id` and calls:

```text
requests.getPurchases(profile.id, {page: currentPage + 1})
```

The builder combines the `customers` prefix with `/{id}/tickets`, substitutes
the customer ID, and defaults the query to `mode=Marjane` plus the supplied page.
Reconstructed request, pending live capture:

```http
GET /customers/{customerId}/tickets?mode=Marjane&page=1
```

Evidence: prefix at 320571–320572; request builder at 321279–321306;
saga at 1606583–1606766. This flow requires a connected profile. The API's actual
authorization enforcement and successful wire response are not yet verified.

State starts with `currentPage=0`, `purchases=[]`, `fetchedAll=false`.
Success appends purchases and increments the page. Force reload clears the list,
resets the page and clears `fetchedAll`. STOP sets `fetchedAll=true`.
The saga dispatches STOP when `response.data` is falsy; do not assume an empty
array ends pagination without checking the actual backend response.
Evidence: 1606219–1606414 and 1606630–1606680.

## List item fields

`ApiPurchaseToPurchaseAdapter`, lines 1477305–1477426, maps:

```text
ticket_key         → ticketNumber
server             → shop.id (parseInt base 10)
create             → date
ticket_total_price → total (parseFloat)
card_key           → cardNumber
status             → status (parseInt then the status mapping below)
server_label       → serverLabel
```

The saga copies `serverLabel` to `shop.title` (1606698–1606715).
`parsePurchaseDate` takes the first 19 characters, appends ` +00`, parses
`yyyy-MM-dd HH:mm:ss X` and the adapter calls `toISOString()` (684708–684759).
This describes client behavior, not proof of the server timezone.

`parsePurchaseStatus` (1477232–1477297) maps numeric values as follows:
`0 → Created`, `1 → Canceled`, `2 → Deleted`, `3 → Delivered`.
Unrecognized values fall back to `Created`, rather than an unknown status.
The separate `PurchaseStatus` enum defines more labels, but this adapter does
not map any other numeric codes to them.

## Ticket details

Opening a receipt dispatches `shopId` and `ticketNumber`. The saga reads the
signed-in profile and calls:

```text
requests.getPurchase(profile.id, shopId.toString(), ticketNumber)
```

The reconstructed path is:

```http
GET /customers/{customerId}/tickets/{serverId}/{ticketKey}
```

Evidence: builder 321307–321331; saga 1606433–1606537.
The server ID comes from the receipt's `server`, not its display label.

`ApiPurchaseDetailsToPurchaseDetailsAdapter` (1478008–1478275) expects:

```text
ticket                  → ticketNumber, shop, date (via the list adapter)
ticket_total            → total
array_of_item           → items
array_of_triggeritem    → triggerItems
array_of_immediate_reward → immediateReward
array_of_redemption     → redemptions
array_of_counter        → counter
ticket_total_discount   → totalDiscount
ticket_total_price      → totalExcludingBenefits
array_of_coupon         → coupons
array_of_payment_mean   → paymentTypes
```

Item mappings include `name_item → title`, `price → price` (parseFloat),
`quantity → quantity` (parseInt base 10), and `hierarchy → hierarchy`.
Payment mappings include `data_1 → type` and `data_2 → amount` (parseFloat).
Nested adapter evidence: 1477432–1478007. Exact units, nullable fields, payment
type meanings and reward semantics still need a real response; names alone are
not a contract.

Payment enum literals (379920–379943) include `ESPECES`, `CB AUTO`,
`CB MANUELLE`, `CAGNOTTE_TRIMESTRE`, and `Rendu(ESPECES)`, alongside
`Cash`, `Check`, `AmericanExpress`, `MasterCard`, `Voucher`, and `Other`.
These are client-recognized strings, not proof that every value appears in
current receipts. In particular, do not sum payment rows as paid amounts without
checking how cash change (`Rendu(ESPECES)`) is signed in a real response.

## Online history: active Coral API

The active `getOrdersSaga` uses **`services.order.query`**, not the older
`requests.getCustomerOrders` helper. It supplies `sort` by `created_at`
descending, `page`, and `status`; it uses the `content-range` response header to
stop once all orders are loaded (1602281–1602440).

Following the active client further reconstructs this request:

```http
GET https://api-ayaline.marjane.ma/coral/order?sort[created_at]=desc&page=1&status[]=STATUS_DELIVERED
Content-Type: application/json
Authorization: Bearer <session.token>
user-id: <session.userID>
accept-language: <configured language>
```

This example selects the **delivered** filter. Headers are conditional: the
default handler adds Authorization if a session exists; the Coral handler adds
`user-id` only for a truthy session user ID and `accept-language` only when set.
This is client construction, not evidence that the server trusts the user ID
without checking the token. No server authorization weakness has been established.

Trace chain:

- `coralPath = 'coral'` (681380–681381) and `coralApiUrl` built from the base
  URL plus that path (680789–680795).
- App initialization sets `magicoreConfig.coral.url` to `coralApiUrl`
  (308108–308124).
- Order endpoint registers `/order` with method `GET`, API name `coral`, and
  `ordersQuery` schema (441510–441526); `services.order.query` exports that
  endpoint (441634, 443414–443420).
- Query schema accepts optional `sort` (string record), `status` (string array),
  `page` and `page_size` (numbers), and `reference` (string)
  (441354–441409). The history saga does not supply `page_size` or `reference`.
- Query serializer retains bracketed keys: nested `sort` becomes
  `sort[created_at]=desc`, and status arrays become repeated `status[]=...`.
  Values are URI-encoded (420367–420561). Sort direction is `desc`
  (380166–380172).
- Coral headers: 420861–420915; Bearer header: 421517–421574;
  URL construction: 421830–421847.

### Filters

Source: 975117–975190, 975450–975497 and the status enum at 379378–379404.

```text
pending    → STATUS_OPEN_PENDING
finished   → STATUS_FINISHED
validated  → STATUS_VALIDATED
preparing  → STATUS_PREPARING, STATUS_ERROR_PAYMENT
ready      → STATUS_READY
delivering → STATUS_DELIVERING
delivered  → STATUS_DELIVERED
annulled   → STATUS_CANCELLED
```

**All** concatenates the above groups except `pending`. It therefore sends eight
status strings; it is not an unfiltered query. The client also displays
`STATUS_FINISHED` through the validated category in `getByStatus`
(975223–975246). This is distinct from the numeric in-store receipt statuses.

`convertContentRangeToMetadata` searches for `(digits)-(digits)/(digits)` in the
header and returns `start`, `end`, and `total` as **strings**. An empty header or
one without that pattern returns undefined; wildcard totals do not match
(1576882–1576934). The saga compares the loaded array length with `total` using
JavaScript's numeric coercion. No default online page size is established here.

The bundle also contains older order helpers and adapters, including an adapter
that turns `page` into `range` with a default limit of 50. Their existence does
**not** establish that the current screen uses that encoding.
`/front/customers/orders` is not the active endpoint traced above.
Earlier HTTP probes returned 401/403/404/405, not successful order data; those
statuses alone cannot validate the screen's complete request contract.

## Device verification and next steps

ADB is authorized and root was verified with `uid=0(root)` through Magisk.
A temporary localhost-only Frida server and scoped OkHttp hook captured two
order-summary requests. A native app crash occurred during instrumentation;
Frida is suspected but the cause is not proven. The server was stopped and
further live instrumentation is paused. No ADB tap commands were used.
No app data files have been extracted and the APK has not been modified.
The temporary UI hierarchy dump was removed. A later, owner-approved HTTPS proxy
experiment used a temporary app-namespace trust mount, but its device-wide proxy
setting disrupted connectivity when USB forwarding disappeared. The proxy
settings were restored and the proxy process stopped; see
[proxy experiment and safety caveat](proxy-experiment.md).

The investigation subsequently moved to the official website and verified
receipt-list/detail field structures without phone access. The Firefox exporter
uses browser-local observation instead of a device-wide proxy; see
[browser findings](browser-history.md).
Keep tokens, customer IDs, loyalty numbers and raw receipts out of Git and chat.
Do not try other customer IDs, place orders, redeem rewards or change balances.

## Reproducible lexical evidence index

```sh
python3 scripts/extract_api.py work/bundle_js -o work/api
python3 -m unittest discover -s tests
```

`work/api/evidence.json` records purchase adapter mapping pairs, source line
numbers, source SHA-256 and path-literal candidates. It is deliberately not a
complete API schema extractor: it does not interpret control flow, transforms,
HTTP methods or authentication. The earlier general schema-extraction attempt
did not produce a trustworthy endpoint inventory and was replaced.

An offline request-target builder captures the traced paths and filter behavior:

```sh
python3 scripts/history_requests.py online --filter delivered --page 1
python3 scripts/history_requests.py receipts CUSTOMER_ID --page 1
python3 scripts/history_requests.py detail CUSTOMER_ID SERVER_ID TICKET_KEY
```

It prints relative URLs only: no network, authentication or device access.
Use placeholders in examples and only your own customer/receipt identifiers for
later authorized verification. The helper URL-encodes path segments defensively;
this is intentionally stricter than the decompiled interpolation, not a claim
of identical behavior for malformed IDs.
